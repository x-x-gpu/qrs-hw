# 智能网关 MILP 算法核心设计报告

日期：2026-06-18

## 1. 报告范围

本报告说明 PC 端智能网关求解器的建模思路、输入输出、目标函数、约束设计和测试方式。它对应仓库中的 `code/pc_milp_solver/gateway_milp.py` 与 `code/protocol/qrs_frames.py`。硬件侧提供传感器数据，算法侧把这些数据转化为 LED、蜂鸣器、风扇代理变量和空调代理变量的控制策略，最终生成 STM32 能够解析的 `@C` 控制帧。

本次课程题目要求体现智能网关和优化决策，因此我没有只写一个固定阈值 if-else，而是把问题组织成 0-1 决策变量、线性目标函数和功率约束的形式。由于演示规模较小，当前代码用枚举方式遍历全部 0/1 组合；变量增加后可以平滑迁移到 PuLP、OR-Tools 或其他 MILP 求解器。

## 2. 数据流与代码位置

```text
ESP32/STM32 @D 数据帧
  -> qrs_frames.py 解析字段
  -> gateway_server.py 更新状态
  -> gateway_milp.py 求解 0-1 控制策略
  -> qrs_frames.py / gateway_milp.py 生成 @C 控制帧
  -> USART1 返回 STM32
```

| 文件 | 作用 | 关键内容 |
|---|---|---|
| `code/pc_milp_solver/gateway_milp.py` | MILP 风格求解核心 | 设备定义、收益函数、功率约束、枚举求解、控制帧生成 |
| `code/pc_milp_solver/gateway_server.py` | 本地网页后端 | HTTP 接口、状态缓存、串口自动转发、ACK 读取 |
| `code/protocol/qrs_frames.py` | 协议工具 | `@D` 解析、字段类型转换、`@C` 编码 |
| `frontend/index.html`、`frontend/app.js` | 浏览器可视化 | 参数编辑、求解按钮、结果展示 |
| `data/` | 样例与最近状态 | 便于演示和复现 |

## 3. 输入变量设计

算法输入分为硬件采集量和用户设置量。硬件采集量来自 ESP32 节点经 STM32 汇总后的 `@D` 帧；用户设置量来自网页控制台，用于体现不同用电策略下的调度变化。

| 变量 | 来源 | 类型 | 建模含义 |
|---|---|---|---|
| `PIR` | HC-SR501 | 0/1 | 是否有人活动，影响照明和告警优先级 |
| `LUX` | BH1750 | 连续量 | 光照强度，低光照时提升 LED 收益 |
| `T` | AM2302/DHT22 | 连续量 | 温度，超过目标温度时提升风扇/空调收益 |
| `H` | AM2302/DHT22 | 连续量 | 湿度，作为环境状态展示和扩展约束 |
| `BH` | 节点状态 | 枚举文本 | 判断光照传感器是否可靠 |
| `DHT` | 节点状态 | 枚举文本 | 判断温湿度传感器是否可靠 |
| `price` | 网页设置 | 连续量 | 电价，抑制高功耗设备 |
| `power_limit_w` | 网页设置 | 整数 | 总功率上限 |
| `target_temp_c` | 网页设置 | 连续量 | 舒适温度目标 |

网页端可以直接修改这些输入，便于答辩时展示同一硬件数据在不同电价、功率上限和目标温度下的策略变化。

## 4. 决策变量设计

当前演示规模下定义四个 0-1 决策变量：

| 变量 | 设备含义 | 功率估计 | 说明 |
|---|---|---|---|
| `LED` | 照明控制 | 8 W | 与实际 STM32 LED/LCD 状态绑定，低光照有人时优先打开 |
| `BUZZER` | 告警蜂鸣器 | 2 W | 用于异常、传感器故障或演示告警 |
| `FAN_PROXY` | 风扇代理变量 | 120 W | 当前 LCD 展示，代表后续可接继电器负载 |
| `AC_PROXY` | 空调代理变量 | 1500 W | 高功率负载代理，主要体现功率约束与电价影响 |

这里的 `FAN_PROXY` 和 `AC_PROXY` 暂时不是实际接线的风扇和空调，而是楼宇设备代理变量。这样既能满足智能网关优化调度的题目要求，又不会在课程现场引入高压负载风险。

## 5. 目标函数

求解目标可以概括为：在总功率不超过上限的前提下，最大化舒适度与安全收益，减去能源成本。

```text
maximize  comfort_reward(x, sensor_state) - energy_cost(x, price)
subject to sum(power_i * x_i) <= power_limit_w
           x_i ∈ {0, 1}
```

代码中将每个设备定义为 `Device(key, command_name, power_w, base_reward)`。求解时对四个二进制变量枚举全部组合，先过滤超过功率上限的组合，再计算收益：

```text
total_power = Σ power_i * x_i
cost        = total_power / 1000 * price
objective   = reward - cost
```

收益项根据传感器状态动态调整。例如，光照低且有人时，LED 组合会得到更高收益；温度高于目标温度时，风扇和空调代理变量的收益提高；传感器异常或需要提示时，蜂鸣器变量得到告警收益。这样网页修改输入后，目标函数和输出帧会同步变化。

## 6. 约束设计

当前实现中的硬约束主要是功率限制，软逻辑通过收益函数体现。

| 约束/规则 | 类型 | 作用 |
|---|---|---|
| `sum(power_i * x_i) <= power_limit_w` | 硬约束 | 防止同时开启高功耗设备导致超限 |
| `x_i ∈ {0,1}` | 硬约束 | 所有设备开关为二进制状态 |
| 低光照且有人提高 LED 收益 | 软规则 | 让照明策略符合直觉 |
| 温度越高越提高 FAN/AC 收益 | 软规则 | 体现舒适温控目标 |
| 电价越高成本越大 | 软规则 | 让高功耗动作受用电成本抑制 |
| 传感器异常触发告警收益 | 软规则 | 保留安全提示能力 |

选择这种设计的原因是演示时更容易解释：硬约束保证安全边界，目标函数体现偏好，网页参数改变则改变最优解。

## 7. 输出控制帧

求解结果会被编码为 STM32 端可以解析的 ASCII 文本帧：

```text
@C,LED=1,BUZZER=0,FAN=1,AC=1*00
```

字段含义如下：

| 字段 | 取值 | STM32 侧行为 |
|---|---|---|
| `LED` | 0/1 | 更新 LCD 显示，并尝试驱动板载 LED0 |
| `BUZZER` | 0/1 | 更新 LCD 显示，并尝试驱动蜂鸣器 |
| `FAN` | 0/1 | 更新 LCD 上的风扇代理状态 |
| `AC` | 0/1 | 更新 LCD 上的空调代理状态 |
| `*00` | 文本校验占位 | 当前演示保留格式，后续可替换为 XOR/CRC |

`@C` 帧保持为纯文本，是为了方便 XCOM、Python 后端和 STM32 裸机程序同时调试。实际产品中可以改成二进制帧或带 CRC 的文本帧。

## 8. 测试方法

命令行测试用于确认算法和协议在没有硬件时也能独立运行：

```powershell
cd .\code\pc_milp_solver
python .\gateway_milp.py
python ..\protocol\qrs_frames.py --frame "@D,ID=01,PIR=1,LUX=118.4,T=29.1,H=63.5,BH=ESP_OK,DHT=ESP_OK"
```

网页测试用于确认本地控制台可以展示和修改状态：

```powershell
python .\gateway_server.py
```

浏览器访问：

```text
http://127.0.0.1:8765
```

如果要自动返回 STM32，可以运行：

```powershell
python .\gateway_server.py --serial-port COM3
```

此时网页点击求解后，后端会把 `@C` 帧写入串口，并尝试读取 `ACK @C UPD=n`。

## 9. 算法调试记录

开发过程中我刻意保留了两层可调试入口：命令行入口用于验证模型和协议，网页入口用于展示人机交互。这样可以避免一出问题就分不清是算法错误、前端错误还是串口错误。

| 问题 | 检查方式 | 结论 |
|---|---|---|
| 网页数值不变 | 先运行 `gateway_milp.py`，再看浏览器接口 | 若命令行正常，问题多半在前端状态刷新 |
| `@D` 解析失败 | 用 `qrs_frames.py --frame` 单独测试 | 字段名或帧头不匹配会直接报错 |
| `NO REPLY` 被误解 | 对比 LCD `MILP CTRL` 的 `UPD` | `NO REPLY` 是 RS485 节点回包问题，不代表 MILP 控制帧失败 |
| 自动串口失败 | 看 Python `[serial]` 日志 | COM 口被占用或未安装 `pyserial` 会在终端显示 |

## 10. 本阶段小结

本阶段完成了从传感器状态到控制策略的算法闭环。它不是单纯的网页模拟，也不是只在 STM32 上显示固定字符串，而是把硬件数据、网页参数、优化求解和控制帧统一到了同一套协议中。后续接口对齐阶段的重点，就是让 `@C` 帧稳定进入 STM32，并在 LCD 和串口日志中可见。
