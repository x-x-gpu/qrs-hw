# STM32 与 QRS 硬件接口对齐报告

日期：2026-06-19

## 1. 报告范围

本报告说明我负责的 MILP 控制链路如何与队友已有的 QRS 硬件采集链路对齐。这里的“接口对齐”不是只列协议格式，而是要确认三类帧在不同物理通道上的方向、波特率、解析位置和调试证据，避免把 RS485、USART1 和 SWD/JTAG 混在一起。

系统中同时存在三条重要链路：ESP32-C6 节点通过 RS485 向 STM32 返回 `@D` 数据帧；STM32 通过 RS485 向 ESP32 发送 `@Q` 轮询帧；PC 通过 USART1 向 STM32 发送 `@C` 控制帧。三者都是文本帧，但物理通道不同。

## 2. 总体数据方向

```text
ESP32-C6 传感器节点
  <- RS485 @Q 轮询帧
  -> RS485 @D 数据帧
STM32 战舰 V3 主站
  -> LCD 显示节点状态
  <- USART1 @C 控制帧
PC 本地 MILP 后端 / 网页控制台
```

| 帧类型 | 发送方 | 接收方 | 通道 | 作用 |
|---|---|---|---|---|
| `@Q` | STM32 | ESP32-C6 节点 | USART3 + RS485 | 点名查询节点 |
| `@D` | ESP32-C6 节点 | STM32 / PC | RS485 或网页粘贴 | 上传传感器状态 |
| `@C` | PC MILP 后端 | STM32 | USART1 / USB 串口 | 返回控制策略 |
| `ACK` | STM32 | PC | USART1 / USB 串口 | 确认控制帧已解析 |

这样划分后，某条链路失败时可以定向排查。例如 LCD 上节点区域 `NO REPLY` 多半是 `@Q/@D` RS485 链路问题；而 `MILP CTRL` 的 `UPD` 不增加，则应检查 `@C` 控制链路。

## 3. 上行数据帧 `@D`

队友硬件链路稳定后，ESP32-C6 节点会返回类似数据帧：

```text
@D,ID=01,PIR=1,LUX=118.4,T=29.1,H=63.5,BH=ESP_OK,DHT=ESP_OK
```

| 字段 | 含义 | 算法侧用途 |
|---|---|---|
| `ID` | 节点编号 | 区分多节点数据来源 |
| `PIR` | 人体红外检测结果 | 判断是否有人活动 |
| `LUX` | 光照强度 | 影响 LED/照明收益 |
| `T` | 温度 | 影响 FAN/AC 收益 |
| `H` | 湿度 | 展示环境状态，后续可加入舒适度约束 |
| `BH` | BH1750 状态 | 判断光照数据是否可信 |
| `DHT` | AM2302/DHT22 状态 | 判断温湿度数据是否可信 |

PC 端 `code/protocol/qrs_frames.py` 可以解析该帧，并转换为 MILP 求解器使用的字段。网页演示时既可以使用默认样例，也可以复制队友串口日志中的真实 `@D` 帧进行求解。

## 4. 轮询帧 `@Q`

STM32 主站通过 RS485 轮询节点：

```text
@Q,ID=01*00
@Q,ID=02*00
```

这部分沿用队友工程的主站逻辑，我的修改不改变轮询节奏和节点显示。保留 `@Q/@D` 链路的原因是它能证明系统数据来源于真实传感器，而不是网页里手填的静态样例。MILP 网关工程是在这个基础上增加 PC 控制侧通道。

## 5. 控制帧 `@C`

PC 端求解后生成控制帧：

```text
@C,LED=1,BUZZER=0,FAN=1,AC=0*00
```

STM32 端收到后执行三件事：第一，解析 LED、BUZZER、FAN、AC 四个字段；第二，更新 LCD 中的 `MILP CTRL` 区域；第三，向串口返回 ACK，方便 Python 后端和串口助手判断链路是否通。

```text
STM32 MILP UART1 READY
ACK @C UPD=1
```

LCD 预期显示类似：

```text
MILP CTRL  UPD:1
LED:ON  BZ:OFF
FAN:ON  AC:OFF
U1 RX:37  OV:0
```

其中 `UPD` 是已成功解析的 `@C` 帧数量，`U1 RX` 是 USART1 收到的字节数，`OV` 是接收环形缓冲溢出次数。加入这些调试量后，即使物理 LED 或蜂鸣器因为板卡版本、电平或跳线没有动作，也能判断控制帧是否已经进入 STM32 程序。

## 6. STM32 固件改动点

`stm32-warship-v3-milp-gateway/` 是从 RS485 主站工程派生出的副本。主要改动集中在 `main.c` 和 `startup.c`。

| 文件 | 改动 | 目的 |
|---|---|---|
| `main.c` | 增加 USART1 寄存器定义、初始化和中断接收 | 接收 PC 端 `@C` 控制帧 |
| `main.c` | 增加控制帧解析函数 | 将文本字段转成 LED/BZ/FAN/AC 状态 |
| `main.c` | 增加 LCD `MILP CTRL` 区域 | 现场可视化控制结果 |
| `main.c` | 增加 ACK 输出 | 便于 Python 后端确认发送结果 |
| `startup.c` | 增加 `USART1_IRQHandler` 弱符号和向量表项 | 让 USART1 中断真正进入处理函数 |
| `Makefile` | 保持已有裸机编译流程 | 确保工程可用 `make` 构建 |

我在调试中发现，如果只写了 `USART1_IRQHandler` 函数但没有在启动文件向量表中放入正确入口，程序不会进入中断处理。这也是后来 `U1 RX` 不增加的关键原因之一。修正 `startup.c` 后，发送 `@C` 帧可以看到 RX 计数变化和 ACK 返回。

## 7. 物理连接与参数

| 项目 | 当前设置 | 说明 |
|---|---|---|
| PC 到 STM32 控制口 | USART1 / USB 转串口 | 用于 `@C` 和 ACK |
| 控制口波特率 | 115200 8N1 | 与 Python 后端和 XCOM 保持一致 |
| STM32 到 ESP32 | USART3 + RS485 模块 | 沿用队友 RS485 链路 |
| 烧录调试 | ST-Link / SWD | 只用于 `make flash`，不接收普通串口帧 |
| LED | PB5，低电平有效 | 不同板卡可能需按原理图校正 |
| 蜂鸣器 | PB8 | 与板载电路有效电平有关 |

这里再次强调，SWD/JTAG 口不是普通串口。把 USB 线插在 ST-Link 口上可以烧录成功，但并不代表 XCOM 打开的 COM 口就是 USART1。

## 8. 接口验证步骤

推荐按以下顺序验证接口：

1. 烧录 `stm32-warship-v3-milp-gateway` 固件，确认 LCD 出现 `MILP CTRL` 区域。
2. 打开正确的 USB 串口，设置 115200 8N1，复位后观察 `STM32 MILP UART1 READY`。
3. 手动发送：

```text
@C,LED=1,BUZZER=0,FAN=1,AC=1*00
```

4. 查看串口是否返回：

```text
ACK @C UPD=1
```

5. 查看 LCD 上 LED、BZ、FAN、AC 和 `UPD` 是否同步变化。
6. 再启动 Python 后端 `--serial-port COM3`，由网页求解自动发送同样格式的控制帧。

## 9. 典型误判与区分

| 现象 | 容易误判 | 实际排查方向 |
|---|---|---|
| LCD 节点区域显示 `NO REPLY` | 以为 PC 控制失败 | 优先检查 RS485 节点回包，和 `@C` 控制链路不同 |
| XCOM 发送无响应 | 以为解析代码错误 | 先看是否接到了 USART1，而不是 SWD/JTAG |
| Python 报 COM3 拒绝访问 | 以为后端代码错误 | Windows 串口被 XCOM 占用，关闭其他串口工具 |
| `U1 RX` 增加但 `UPD` 不变 | 以为中断没进 | 帧头、换行或字段格式可能不符合 `@C` 解析要求 |
| LCD 显示 ON 但物理 LED 不亮 | 以为算法没输出 | 控制帧已到达，需检查 GPIO 映射和有效电平 |

## 10. 本阶段小结

接口对齐后，系统中每条链路的职责更加清楚：RS485 链路负责采集数据，PC 链路负责求解和控制返回，LCD 与串口日志负责现场证据。这个阶段的价值在于把“网页上有一个算法”和“板子上有传感器数据”真正连起来，并且给出可排查的中间信号。
