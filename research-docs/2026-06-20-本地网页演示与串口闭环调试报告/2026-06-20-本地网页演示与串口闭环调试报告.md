# 本地网页演示与串口闭环调试报告

日期：2026-06-20

## 1. 报告范围

本报告记录最终演示阶段的网页启动、串口自动转发、STM32 LCD 反馈和若干实际调试问题。与前几份报告相比，本报告更偏“现场复现手册”：老师或同学拿到仓库后，可以按这里的步骤启动网页、生成控制帧、观察 STM32 是否收到，并知道常见报错应该从哪里查起。

演示目标不是只打开一个静态网页，而是形成如下闭环：

```text
网页修改输入
  -> Python 后端调用 MILP 求解器
  -> 生成 @C 控制帧
  -> 串口发送到 STM32 USART1
  -> STM32 返回 ACK 并刷新 LCD
```

如果 ESP32/RS485 节点也同时在线，则可以把真实 `@D` 数据引入网页状态，使演示更完整。

## 2. 启动本地控制台

进入 PC 后端目录：

```powershell
cd .\code\pc_milp_solver
python .\gateway_server.py
```

浏览器打开：

```text
http://127.0.0.1:8765
```

页面会显示智能网关控制台，包含传感器输入、求解结果、控制策略、功率和返回控制帧。演示时可以调整目标温度、电价、功率上限、光照、温度、湿度和 PIR 状态，然后点击“求解并生成控制帧”。

| 页面区域 | 演示作用 |
|---|---|
| 传感器输入 | 说明数据来自 `@D` 帧或手动模拟 |
| 运行参数 | 调整电价、功率上限、目标温度 |
| 求解结果 | 展示目标函数、总功率、控制变量 |
| 控制帧 | 展示发送给 STM32 的 `@C` 文本 |
| 串口状态 | 启用自动转发后显示发送和 ACK 情况 |

## 3. 自动串口转发

如果已经确认 COM 口对应 STM32 USART1，可以启动自动转发：

```powershell
python .\gateway_server.py --serial-port COM3
```

此时后端会独占 COM3。网页每次求解生成新的 `@C` 帧后，Python 会把帧写入串口，并尝试读取 STM32 返回的 ACK。终端中应看到类似日志：

```text
Serial port configured: COM3 at 115200 baud
  [serial] Sent to COM3: @C,LED=1,BUZZER=0,FAN=1,AC=1*00
  [serial] STM32 replied: ACK @C UPD=1
```

如果没有启用 `--serial-port`，网页仍然可以正常求解并显示 `@C` 帧，只是不会自动发给 STM32。这种模式适合先检查算法和前端，再用 XCOM 手动发送帧。

## 4. STM32 端观察点

烧录 `stm32-warship-v3-milp-gateway` 后，LCD 应同时保留 RS485 节点状态和新增的 MILP 控制状态。控制帧链路是否成功，主要看以下几个量：

| 观察量 | 正常表现 | 含义 |
|---|---|---|
| `MILP CTRL` | LCD 下方出现控制区域 | 固件包含 MILP 显示逻辑 |
| `UPD` | 每收到有效 `@C` 增加一次 | 控制帧解析成功次数 |
| `U1 RX` | 发送串口数据后增加 | USART1 确实收到字节 |
| `OV` | 通常保持 0 | 接收缓冲未溢出 |
| 串口 READY | 复位后输出 `STM32 MILP UART1 READY` | USART1 初始化成功 |
| 串口 ACK | 输出 `ACK @C UPD=n` | STM32 完成帧解析 |

这些观察点比单纯看 LED 或蜂鸣器更可靠。因为板卡版本、跳线和有效电平可能让物理执行器表现不明显，但 LCD 和 ACK 可以先证明控制链路已经通了。

## 5. 推荐演示流程

完整答辩演示可以按下面顺序进行：

1. 先展示 `qrs-hw` 根目录 README，说明系统闭环和分工。
2. 展示 ESP32/RS485/STM32 原始链路，LCD 上能看到节点数据或节点状态。
3. 切换到 `stm32-warship-v3-milp-gateway`，说明这是在原主站基础上增加控制帧入口的副本。
4. 启动 `python .\gateway_server.py`，打开 `http://127.0.0.1:8765`。
5. 修改网页输入，点击求解，观察目标函数、功率和 `@C` 帧变化。
6. 启动 `--serial-port COM3` 或用 XCOM 手动发送 `@C`。
7. 观察 STM32 串口 ACK 和 LCD `MILP CTRL` 区域更新。
8. 最后解释 `FAN`、`AC` 当前是代理变量，LED/BZ 是板载可观察执行端。

## 6. 调试问题 1：编译警告变错误

曾经出现过如下构建错误：

```text
main.c:187:13: error: 'lcd_is_nt35510' defined but not used [-Werror=unused-variable]
cc1.exe: all warnings being treated as errors
make: *** [Makefile:24: build/main.o] Error 1
```

原因是 Makefile 中启用了 `-Werror`，未使用变量会从 warning 变成 error。这个问题不是 LCD 驱动本身坏了，而是新增代码时留下了未参与逻辑的变量。解决思路是回到可编译基线，再按实际需要修改：如果变量不需要就删除；如果需要区分 LCD 型号，就必须让它参与显示初始化或分支逻辑。

这次问题提醒我，嵌入式工程里“能不能编译通过”经常受编译选项影响。为了避免把无关改动带入工程，后续只在 `stm32-warship-v3-milp-gateway/` 副本里修改，不碰队友原始工程。

## 7. 调试问题 2：OpenOCD 烧录失败

执行 `make flash` 时曾出现：

```text
Open On-Chip Debugger 0.12.0
Error: open failed
** OpenOCD init failed **
make: *** [Makefile:33: flash] Error 1
```

这个错误发生在 OpenOCD 打开调试器阶段，说明问题更可能在 ST-Link、USB 线、驱动、供电或板卡连接，而不是 `warship_v3_milp_gateway.elf` 本身。重新检查连接后，烧录成功，LCD 上出现新增的 `MILP CTRL` 内容。

## 8. 调试问题 3：XCOM 发送无响应

一开始我已经在 XCOM 中发送控制帧，但 STM32 没有任何响应。当时 USB 线接在 SWD/JTAG 口，这只能用于下载调试，不能当作 USART1 普通串口。后来改接正确的 USB 转串口通道，并设置 115200 8N1 后，复位能看到：

```text
STM32 MILP UART1 READY
```

发送：

```text
@C,LED=1,BUZZER=0,FAN=1,AC=1*00
```

可以收到：

```text
ACK @C UPD=1
```

同时 LCD 的 `UPD`、LED、BZ、FAN、AC 状态会更新。

## 9. 调试问题 4：COM3 拒绝访问

运行：

```powershell
python .\gateway_server.py --serial-port COM3
```

曾出现：

```text
[serial] Failed to send to COM3: could not open port 'COM3': PermissionError(13, '拒绝访问。', None, 5)
```

Windows 下串口通常是独占资源。如果 XCOM 已经打开 COM3，Python 后端就不能再打开同一个端口。解决方法是关闭 XCOM，由 Python 后端独占串口；或者关闭 Python 后端，再用 XCOM 手动发送，两者不要同时占用同一个 COM 口。

## 10. 调试问题 5：网页显示 NO REPLY

网页或 LCD 上看到 `NO REPLY` 时，不能立刻判断 MILP 控制失败。`NO REPLY` 主要表示 STM32 在 RS485 轮询 ESP32 节点时没有收到 `@D` 回包，可能与节点供电、A/B 接线、RS485 方向控制或节点程序有关。

判断 PC 到 STM32 的 `@C` 控制链路，应看下面三个证据：

1. Python 终端是否显示 `Sent to COM3`。
2. STM32 是否返回 `ACK @C UPD=n`。
3. LCD 的 `MILP CTRL` 中 `UPD` 是否增加。

如果这三项正常，即使节点区域暂时显示 `NO REPLY`，也说明 MILP 控制帧链路是通的。

## 11. 调试问题 6：LCD 显示 ON 但物理执行器无动作

曾出现 LCD 上 `LED` 和 `BZ` 显示为 ON，但肉眼没有看到 LED 亮、蜂鸣器也没有响的情况。这个现象说明算法策略已经到达 STM32，但物理执行还需要单独检查 GPIO 映射、有效电平和板卡跳线。

当前固件按常见战舰 V3 接法使用 PB5 作为 LED0，PB8 作为蜂鸣器，其中 LED 可能是低电平有效。不同板卡版本或外设跳线不同，实际现象可能与代码假设不一致。为了演示稳妥，答辩时应同时展示 LCD 状态、串口 ACK 和必要时的 GPIO 说明，而不是只依赖蜂鸣器声音。

## 13. 最终状态

截至 2026-06-20，本地网页可以正常求解并生成 `@C` 控制帧；STM32 MILP 网关可以烧录运行，LCD 能显示新增控制区域；USART1 通道可以通过串口助手或 Python 后端接收控制帧并返回 ACK。剩余需要现场确认的主要是实际板卡 LED/蜂鸣器的电平与接线，以及 ESP32/RS485 节点在线状态。
