ESP32-C6 多节点 RS485 采集系统软件调试报告

日期：2026-05-31

1. 报告范围

本报告只整理本次项目的软件部分。硬件接线、供电、GND、RS485 A/B 主干、战舰 V3 与 ESP32-C6 节点的端子级连接，已经在上一份硬件方案报告中给出，本文不重复画接线图，只在必要处引用当前软件默认的引脚和通信参数。

本次软件系统由三部分组成：

  1. 两块 ESP32-C6 采集节点：读取 BH1750 光照、AM2302 温湿度、HC-SR501 PIR 状态，并在 RS485 总线上被点名后返回数据。
  2. 战舰 V3 / STM32F103ZET6 主站：通过外置 RS485 模块轮询两个 ESP32-C6 节点，解析应答，维护在线状态和统计窗口。
  3. 战舰 V3 自带 LCD 显示与串口诊断：LCD 显示两个节点的状态、传感器值、超时次数和接收诊断；串口输出 @A、@Q,DBG 等文本帧用于排障。

最终稳定版本采用：

主站串口STM32 USART3
战舰侧 TX/RX/方向控制PB10 / PB11 / PF12

3. 通信协议与数据流

3.1 主从关系

系统采用“战舰 V3 主站轮询，ESP32-C6 节点被动应答”的方式。两个 ESP32 节点不会主动发送采集数据，只有收到对应 ID 的查询帧时才应答，这样可以避免多个节点同时驱动 RS485 总线。

当前节点 ID 由 ESP32 的 Wi-Fi MAC 末字节映射得到：

节点MAC 末字节节点 ID
ESP32-C6 节点 10x2401
ESP32-C6 节点 20xEC02

3.2 文本帧格式

调试阶段使用 ASCII 文本帧，便于串口助手和 ESP-IDF monitor 直接观察。

主站请求：

@Q,ID=01*00\r\n
@Q,ID=02*00\r\n

节点应答：

@D,ID=01,PIR=0,LUX=257.5,T=28.2,H=69.0,BH=ESP_OK,DHT=ESP_OK\r\n

主站汇总：

@A,SUM,01=OK,S=77,T=600,P=0/4,L=257.1,C=28.2,H=68.9;02=OK,S=16,T=660,P=0/4,L=26.7,C=28.0,H=80.6\r\n

主站逐次诊断：

@Q,DBG=01,OK,L=61,N=61,E=386,Z=1688,S=0000,G=--/--/--/--
@Q,DBG=02,OK,L=60,N=60,E=372,Z=1667,S=0000,G=--/--/--/--

其中 L 是本次解析得到的帧长度，N 是 USART3 接收中断收到的字节数，S 是串口错误位。稳定状态下两个节点的 S 均为 0000。

4. ESP32-C6 节点软件设计

ESP32-C6 节点程序集中在 esp32-wroom-c6-workspace/main/app_main.c。当前主要引脚定义如下：

功能GPIO
BH1750 SDAGPIO6
BH1750 SCLGPIO7
HC-SR501 OUTGPIO10
AM2302 DATAGPIO11
RS485 DE 与 /REGPIO18
RS485 TXGPIO20
RS485 RXGPIO21

节点初始化流程为：

  1. 读取 ESP32-C6 MAC，确定节点 ID。
  2. 初始化 PIR GPIO 输入。
  3. 初始化 AM2302 单总线 GPIO。
  4. 初始化 I2C 并扫描 BH1750 地址，默认支持 0x23 和 0x5C。
  5. 初始化 UART1，配置 RS485 TX/RX 引脚和方向控制引脚。
  6. 进入主循环，持续刷新传感器缓存并处理 RS485 查询帧。

采样节奏如下：

数据当前策略原因
PIR主循环每次读取数字量，读取开销小
BH1750约 200 ms 读取一次光照变化较慢，I2C 读数可中频刷新
AM2302约 2 s 读取一次DHT/AM2302 本身不适合高频读取
RS485 协议处理主循环约 5 ms 检查一次保证查询帧能及时被解析

当收到 @Q,ID=xx 且 ID 与本节点匹配时，节点先等待 RS485_RESPONSE_DELAY_MS，再拉高 GPIO18 进入发送态，发送完整 @D 数据帧，等待 UART 发送完成后回到接收态。

最终稳定参数为：

#define RS485_UART_BAUD_RATE 38400
#define RS485_RESPONSE_DELAY_MS 120

本项目曾尝试把响应延迟降到 10 ms 以追求 10Hz 级别刷新，但在当前战舰 V3 主站接收实现和现场布线条件下，节点 02 会出现 STM32 只收到残字节的问题。最终先采用 120 ms 保证两节点稳定在线。

5. 战舰 V3 主站软件设计

战舰 V3 主站程序集中在 stm32-warship-v3-rs485-test/main.c。当前软件不依赖 STM32 HAL 库，而是直接配置 RCC、GPIO、USART3、SysTick、FSMC LCD 等寄存器。

5.1 串口与方向控制

当前主站使用 USART3：

功能STM32 管脚软件配置
RS485 TXPB10USART3_TX 复用推挽输出
RS485 RXPB11USART3_RX 输入
RS485 方向控制PF12GPIO 输出，发送置 1，接收置 0

初始化时配置：

#define USART3_BRR_38400 0x00D0U
USART3_BRR = USART3_BRR_38400;
USART3_CR3 = USART_CR3_EIE;
USART3_CR1 = USART_CR1_UE | USART_CR1_TE | USART_CR1_RE | USART_CR1_RXNEIE;

其中 RXNEIE 用于打开 USART3 接收中断，EIE 用于捕获帧错误、噪声、溢出等异常。

5.2 USART3 中断接收与环形缓冲

早期版本使用主循环轮询 USART3_SR 和 USART3_DR。在提高波特率和缩短节点响应延迟后，STM32 端经常出现 ORE，表现为屏幕 No reply、调试帧 S=0008 或 S=000A。因此最终改为中断接收。

当前实现要点：

  1. startup.c 中将 USART3 IRQ39 接到 USART3_IRQHandler。
  2. main.c 中维护 256 字节环形缓冲区。
  3. ISR 中先读 SR，再读 DR，按 STM32F1 的规则清除 RXNE/ORE/FE/NE。
  4. 无错误字节进入环形缓冲区，有错误则记录错误位。
  5. 主循环只从环形缓冲区取字节并解析完整 @...\n 文本帧。

这样可以避免 LCD 绘制、软件延时、字符串处理等主循环任务影响 UART 收字节。

5.3 LCD 显示与 5s 汇总

LCD 当前每 5s 刷新一次。显示内容包括：

显示内容含义
ID01 OK/LOST、ID02 OK/LOST节点在线状态
PIR、L、T、H5s 窗口内聚合后的传感器值
BH、DHTESP-IDF 返回的传感器读数状态
S01/T01、S02/T02成功样本数和超时次数
R01/R02 L/N/E/Z/S接收诊断信息

5s 窗口内，LUX/T/H 取平均值，PIR 显示窗口内高电平次数和样本数。由于 AM2302 本身约 2s 更新一次，即使 RS485 查询更频繁，温湿度字段也会重复最近一次有效读数。

6. 关键代码解读

本节按工程模块解释当前代码如何完成采集、轮询、接收、显示和诊断。行号基于当前工作区源码，后续若继续修改代码，行号可能发生变化，但函数职责不变。

6.1 ESP32-C6 节点：引脚、ID 与基础参数

ESP32 节点的核心配置集中在 esp32-wroom-c6-workspace/main/app_main.c 开头。代码第 23-38 行定义了所有外设引脚和 RS485 参数：BH1750 使用 GPIO6/GPIO7，PIR 使用 GPIO10，AM2302 使用 GPIO11，RS485 使用 GPIO20/GPIO21/GPIO18，波特率为 38400，响应延迟为 120ms。

#define BH1750_SDA_GPIO GPIO_NUM_6
#define BH1750_SCL_GPIO GPIO_NUM_7
#define PIR_OUT_GPIO GPIO_NUM_10
#define AM2302_DATA_GPIO GPIO_NUM_11
#define RS485_DE_RE_GPIO GPIO_NUM_18
#define RS485_TX_GPIO GPIO_NUM_20
#define RS485_RX_GPIO GPIO_NUM_21
#define RS485_UART_BAUD_RATE 38400
#define RS485_RESPONSE_DELAY_MS 120

节点 ID 在 init_node_id() 中生成。代码第 54-65 行读取 Wi-Fi MAC，若末字节为 0x24 则设为 01，若末字节为 0xEC 则设为 02。这样不需要额外拨码开关或烧录不同固件，两块 ESP32 使用同一份程序即可自动分配 ID。

if (mac[5] == 0x24) {
    snprintf(s_node_id, sizeof(s_node_id), "01");
} else if (mac[5] == 0xEC) {
    snprintf(s_node_id, sizeof(s_node_id), "02");
}

这段代码的优点是部署简单，缺点是 ID 绑定到当前两块开发板。如果以后扩展到更多节点，应改成 NVS 配置、串口命令配置或根据完整 MAC 建立节点表。

6.2 ESP32-C6 节点：传感器初始化与采样缓存

BH1750 初始化位于 init_bh1750()，代码第 186-214 行。程序先配置 I2C 主机，时钟为 100kHz，然后依次尝试 0x23 和 0x5C 两个常见地址。找到设备后发送 POWER_ON、RESET 和 CONT_HIGH_RES 命令，进入连续高分辨率测量模式。

const uint8_t candidates[] = {BH1750_ADDR_LOW, BH1750_ADDR_HIGH};
for (size_t i = 0; i < sizeof(candidates); i++) {
    uint8_t addr = candidates[i];
    if (bh1750_write_cmd(addr, BH1750_CMD_POWER_ON) == ESP_OK) {
        (void)bh1750_write_cmd(addr, BH1750_CMD_RESET);
        ESP_ERROR_CHECK(bh1750_write_cmd(addr, BH1750_CMD_CONT_HIGH_RES));
        s_bh1750_addr = addr;
        return ESP_OK;
    }
}

主循环第 509-538 行维护传感器缓存。PIR 每轮都读取，BH1750 每 200ms 读取一次，AM2302 每 2s 读取一次。RS485 应答时不现场阻塞读取传感器，而是直接使用最近一次缓存值。这样可以避免 AM2302 的慢速单总线读取拖慢 RS485 应答。

pir_level = gpio_get_level(PIR_OUT_GPIO);

if (last_bh1750_sample_us == 0 || (now_us - last_bh1750_sample_us) >= 200000) {
    bh1750_read_status = read_bh1750_lux(&lux);
    last_bh1750_sample_us = now_us;
}

if (last_am2302_sample_us == 0 || (now_us - last_am2302_sample_us) >= 2000000) {
    am2302_status = read_am2302(&am2302);
    last_am2302_sample_us = now_us;
}

这也是为什么报告中说“通信可以高频，温湿度不一定高频变化”：RS485 帧可以重复发送最近的 AM2302 读数，但 AM2302 本体不应被 10Hz 读取。

6.3 ESP32-C6 节点：RS485 初始化和方向控制

RS485 初始化在 init_rs485_idle_check()，代码第 216-275 行。程序先把 GPIO18 配置为输出，并置低，让收发器处于接收态。随后配置 UART1 为 38400 8N1，将 TX/RX 映射到 GPIO20/GPIO21，并安装 ESP-IDF UART driver。

gpio_set_level(RS485_DE_RE_GPIO, 0);

uart_config_t uart_config = {
    .baud_rate = RS485_UART_BAUD_RATE,
    .data_bits = UART_DATA_8_BITS,
    .parity = UART_PARITY_DISABLE,
    .stop_bits = UART_STOP_BITS_1,
    .flow_ctrl = UART_HW_FLOWCTRL_DISABLE,
};

uart_set_pin(RS485_UART_PORT,
             RS485_TX_GPIO,
             RS485_RX_GPIO,
             UART_PIN_NO_CHANGE,
             UART_PIN_NO_CHANGE);

发送函数 rs485_send_line() 先拉高 GPIO18 进入发送态，等待 500us，写入 UART，等待发送完成，再延迟 600us，最后拉低 GPIO18 回到接收态。这个顺序对应 RS485 半双工模块常见的 DE 与 /RE 短接接法。

gpio_set_level(RS485_DE_RE_GPIO, 1);
esp_rom_delay_us(RS485_TX_ENABLE_DELAY_US);
uart_write_bytes(RS485_UART_PORT, line, strlen(line));
uart_wait_tx_done(RS485_UART_PORT, pdMS_TO_TICKS(100));
esp_rom_delay_us(RS485_TX_DISABLE_DELAY_US);
gpio_set_level(RS485_DE_RE_GPIO, 0);

如果方向控制线漏接或接错，即使 RS485 TX: 日志显示节点正在发送，A/B 总线上也可能没有正确差分输出。这正是前期漏接 RSE 时出现“ESP32 有日志但主站 no reply”的原因。

6.4 ESP32-C6 节点：帧解析与应答

poll_rs485_protocol() 位于代码第 358-405 行。它每次从 UART driver 中最多读 64 字节，以 @ 作为帧起点，以 \n 作为帧结束，忽略 \r 和空字节。如果中途又遇到 @，说明上一帧可能残缺，直接重新开始收帧。

if (line_len == 0) {
    if (ch != '@') {
        continue;
    }
} else if (ch == '@') {
    line_len = 0;
}

if (ch == '\n') {
    handle_rs485_line(line, line_len, lux, bh1750_status, am2302, am2302_status, pir_level);
    line_len = 0;
    continue;
}

handle_rs485_line() 位于代码第 315-356 行。它先区分帧类型：@Q 是主站查询，@A 是主站确认或汇总，@D 是其它节点数据。只有收到 @Q 且 ID 与本节点匹配时，才组装并发送 @D 应答帧。

snprintf(tx_line,
         sizeof(tx_line),
         "@D,ID=%s,PIR=%d,LUX=%.1f,T=%.1f,H=%.1f,BH=%s,DHT=%s\r\n",
         s_node_id,
         pir_level,
         lux,
         am2302->temperature_c,
         am2302->humidity_percent,
         esp_err_to_name(bh1750_status),
         esp_err_to_name(am2302_status));

vTaskDelay(pdMS_TO_TICKS(RS485_RESPONSE_DELAY_MS));
rs485_send_line(tx_line);

这里的 vTaskDelay(120ms) 是当前稳定性的重要参数。此前将它降到 10ms 后，节点 02 回复过早，STM32 端诊断变成 S=000A。因此当前报告把 120ms 作为稳定档，而不是直接追求最高刷新率。

6.5 STM32 主站：寄存器常量和接收中断

STM32 主站没有使用 HAL，而是直接写寄存器。代码第 70-99 行定义了 USART3 状态位、控制位、波特率、RS485 延时、LCD 刷新周期和环形缓冲大小。当前 USART3_BRR_38400=0x00D0 对应默认 8MHz PCLK1 下的 38400 bps。

#define USART_SR_RXNE (1U << 5)
#define USART_SR_ERR_MASK 0x0FU
#define USART_CR1_RXNEIE (1U << 5)
#define USART_CR3_EIE (1U << 0)
#define USART3_BRR_38400 0x00D0U
#define UART3_RX_RING_SIZE 256U

中断向量在 startup.c 第 23 行声明 USART3_IRQHandler，第 43 行用指定初始化 [55] = USART3_IRQHandler 放入向量表。STM32F103 中 USART3 的 IRQn 为 39，对应 Cortex-M 向量表索引 16 + 39 = 55。

void USART3_IRQHandler(void) __attribute__((weak, alias("Default_Handler")));

__attribute__((section(".isr_vector")))
void (*const g_vectors[])(void) = {
    ...
    [55] = USART3_IRQHandler,
};

主程序中的 USART3_IRQHandler() 位于 main.c 第 185-207 行。ISR 先读 USART3_SR，再读 USART3_DR。这是 STM32F1 清除 RXNE/ORE/FE/NE 的关键顺序。如果状态位显示有错误，则记录错误；如果是正常 RXNE 字节，则写入 256 字节环形缓冲。

uint32_t sr = USART3_SR;
if ((sr & (USART_SR_RXNE | USART_SR_ERR_MASK)) != 0U) {
    uint8_t ch = (uint8_t)USART3_DR;

    if ((sr & USART_SR_ERR_MASK) != 0U) {
        uart3_rx_errors |= sr & USART_SR_ERR_MASK;
    }
    if ((sr & USART_SR_RXNE) != 0U && (sr & USART_SR_ERR_MASK) == 0U) {
        uint16_t next = (uint16_t)((uart3_rx_head + 1U) & (UART3_RX_RING_SIZE - 1U));
        ...
        uart3_rx_ring[uart3_rx_head] = ch;
        uart3_rx_head = next;
    }
}

这段代码是本次软件修复的核心。早期轮询接收时，主循环只要在 LCD 绘制、字符串处理或延时中停留过久，USART 就可能产生 ORE。改成 ISR 后，字节到来时立即被读出，主循环后续只处理缓冲区数据。

6.6 STM32 主站：发送方向控制和清残帧

rs485_send() 位于 main.c 第 853-870 行。发送前先关闭 USART3 RX 中断，拉高 PF12 进入发送态，再逐字节写 USART3。等待 TC 发送完成后，延时、拉低 PF12 回到接收态，最后读一次 SR/DR 清掉可能的本机回显或残留，再重新打开 RX 中断。

uart3_rx_irq_enable(false);
rs485_set_tx(true);
delay_cycles(RS485_TX_GUARD_CYCLES);

while (*text != '\0') {
    uart2_putc(*text++);
}

while ((USART3_SR & USART_SR_TC) == 0) {
}
delay_cycles(RS485_TX_GUARD_CYCLES);
rs485_set_tx(false);
(void)USART3_SR;
(void)USART3_DR;
uart3_rx_irq_enable(true);

uart2_flush_rx() 位于第 1181-1193 行。每次查询前，主站先关闭 RX 中断，清空环形缓冲，再读取硬件 DR 清掉 USART 残留，最后重新打开中断。这样可以避免上一轮残帧混入下一轮节点应答。

uart3_rx_irq_enable(false);
uart3_rx_ring_reset();
for (uint32_t i = 0; i < 16U; i++) {
    uint32_t sr = USART3_SR;
    if ((sr & (USART_SR_RXNE | USART_SR_ERR_MASK)) == 0U) {
        break;
    }
    (void)USART3_DR;
}
uart3_rx_irq_enable(true);

这一组发送和清缓冲逻辑解决了两个实际问题：一是半双工方向切换时可能出现本机回显；二是节点 01 和节点 02 连续轮询时，残留字节可能导致下一轮解析错位。

6.7 STM32 主站：从环形缓冲解析应答

uart2_collect_response() 位于第 1053-1179 行。虽然函数名仍叫 uart2，实际已经使用 USART3。函数内部不再直接轮询 USART3_SR，而是调用 uart3_rx_pop() 从环形缓冲取字节。

解析流程为：

  1. 进入函数时清空当前节点的诊断结构。
  2. 在等待循环中不断从 ring buffer 取字节。
  3. 每收到一个字节就更新 rxne_count，并把等待时间切换到较短的 idle timeout。
  4. 遇到 \n 后形成一行文本，复制到输出缓冲区。
  5. 调用 contains_data_frame_for_node() 判断这行是否为当前 ID 的 @D 帧。
  6. 若是目标节点数据帧，立即返回长度；否则丢弃该行继续等待。

关键片段如下：

if (uart3_rx_pop(&rx_ch)) {
    char ch = (char)rx_ch;
    diag->rxne_count++;
    wait_loops = idle_wait_loops;
    line[line_length++] = ch;

    if (ch == '\n') {
        line[line_length] = '\0';
        last_length = copy_response_line(buffer, capacity, line, line_length);
        if (contains_data_frame_for_node(line, node_id)) {
            return last_length;
        }
        line_length = 0;
        wait_loops = first_byte_wait_loops;
    }
}

这段设计允许总线上出现其它类型帧。例如 ESP32 节点能看到 @A,SUM、另一节点的 @D，STM32 主站也可能收到调试帧或残帧；只有 @D,ID=当前节点 才算本次轮询成功。

6.8 STM32 主站：节点状态、5s 窗口和 LCD

节点状态更新由 update_node_from_frame() 和 mark_node_timeout() 完成。update_node_from_frame() 位于第 1428-1459 行，收到有效 @D 帧后将 ok 置为 true，样本数加一，连续超时清零，并把 PIR、光照、温度、湿度加入 5s 窗口累计值。

node->ok = true;
node->seen = true;
node->samples++;
node->consecutive_timeouts = 0U;
node->window_samples++;

if (parse_field_fixed1(frame, "LUX=", &value10)) {
    node->window_lux10_sum += value10;
}

如果本次轮询没有收到有效帧，则 mark_node_timeout() 第 1410-1426 行会增加超时次数。代码设置了 RS485_LOST_AFTER_TIMEOUTS=3，也就是说已有成功样本的节点不会因为一次偶发丢包立刻变红，而是连续超时达到阈值后才标为 LOST。

5s 窗口汇总由 finalize_node_window() 第 1461-1478 行完成。它用窗口内样本数对 LUX/T/H 求平均，对 PIR 显示“高电平次数/样本数”。随后 update_display_if_due() 第 1907-1922 行每 5s 调用该函数、刷新 LCD，并发送一条 @A,SUM 汇总帧。

if ((uint32_t)(now - *last_lcd_ms) < LCD_REFRESH_MS) {
    return;
}

finalize_node_window(&node01);
finalize_node_window(&node02);
lcd_render_status();
if (RS485_SUMMARY_FRAMES) {
    send_summary_diag();
}

LCD 绘制集中在 lcd_render_status() 第 1589-1632 行。屏幕上方显示 RS485 SENSOR BUS 和 38400 5S AVG，中间显示 ID01/ID02 的状态和环境数据，下方显示 S01/T01、S02/T02 以及 R01/R02 L/N/E/Z/S 诊断行。现场排查时，正是通过这些诊断行确认 T01/T02 增长但 N=1,S=000A，从而判断问题不是主循环停止，而是收到坏帧。

6.9 STM32 主站：主循环轮询顺序

主函数第 1948-1975 行完成系统初始化和永久轮询。初始化顺序是 SysTick、节点状态、板级 USART/GPIO、LCD，然后进入循环。循环中依次查询 ID01、更新显示，再查询 ID02、更新显示，最后等待一个轮询间隔。

while (1) {
    delay_cycles(RS485_BETWEEN_NODES_CYCLES);
    query_node("01");
    update_display_if_due(&last_lcd_ms);
    delay_cycles(RS485_BETWEEN_NODES_CYCLES);
    query_node("02");
    update_display_if_due(&last_lcd_ms);
    delay_cycles(RS485_BETWEEN_ROUNDS_CYCLES);
}

query_node() 第 1848-1872 行负责一次完整轮询：组装 @Q,ID=xx*00，清空 RX，发送请求，等待应答，判断是否包含目标 ID 的 @D 帧。若成功则更新节点数据，失败则累计 timeout。当前 RS485_QUERY_DEBUG_FRAMES=1，所以每次轮询后还会发出一条 @Q,DBG 诊断帧，方便继续观察现场问题。

uart2_flush_rx();
rs485_send(request);
delay_cycles(RS485_AFTER_TX_SETTLE_CYCLES);

int len = uart2_collect_response(node_id, rx_line, (int)sizeof(rx_line));
bool ok = len > 0 && contains_data_frame_for_node(rx_line, node_id);
if (ok) {
    update_node_from_frame(node_id, rx_line);
} else {
    mark_node_timeout(node_id);
}

从结构上看，STM32 主站仍是单线程裸机程序；真正异步的只有 USART3 RX 中断。这样实现简单，适合本次课程项目，但也意味着 LCD 绘制、RS485 发送和协议解析都需要控制执行时间。如果后续要继续提高频率，应优先关闭逐次 DBG，再逐级降低 ESP32 应答延迟。

7. 调试过程与错误复盘

7.1 把 P7 485TX/485RX 误认为远端 A/B

最初排查时曾围绕战舰 V3 P7 的 485TX/485RX、PA2/PA3、PD7/RS485_RE 讨论接线。但实物上没有明确可用的板载 RS485 A/B 外部端子，P7 的 485TX/485RX 更适合理解为板内 RS485 相关 TTL 侧信号，而不是远端差分总线。

修复方法是放弃 P7 路径，采用外置 3.3V RS485 模块，并选择实物验证可用的 USART3 路径：

PB10 / USART3_TX -> 外置 RS485 DI
PB11 / USART3_RX <- 外置 RS485 RO
PF12 / GPIO      -> 外置 RS485 DE 与 /RE

这一路在后续测试中被证明可稳定通信。

7.2 PA3 路径长时间固定高电平

早期测试中，PA3 接收路径表现为固定高电平，没有可靠边沿，主站无法收到 ESP32 回复。该现象可能与 P7 跳帽、板内串口复用或接线位置有关。

修复方法是切换到 PB10/PB11 的 USART3。切换后，在低速稳定参数下已经能收到：

@Q,DBG=01,OK,L=61,N=61,S=0000
@Q,DBG=02,OK,L=60,N=60,S=0000

说明问题不是 ESP32 传感器或协议本身，而是原接收路径不适合作为当前主站入口。

7.3 漏接 RSE / 方向控制线

调试过程中曾出现 ESP32 能接收查询但主站收不到回复的情况。后来确认 ESP32 侧 RSE/DE,/RE 方向控制线曾漏接。RS485 半双工收发器如果方向控制未接好，即使 UART TX 有数据，也不会正确驱动 A/B 总线。

修复方法：

ESP32 GPIO18 -> 本节点 RS485 DE 与 /RE
STM32 PF12   -> 战舰侧外置 RS485 DE 与 /RE

软件中发送前拉高方向控制，发送完成后拉低回到接收态。

7.4 GND 未统一导致通信不稳定

多板供电时曾怀疑三块板的 GND 没有全部连在一起。RS485 是差分通信，但收发器仍需要公共参考地，尤其是桌面短线、非隔离模块和多 USB 供电场景。

修复方法是按硬件报告结论统一 GND：

战舰 GND
战舰侧 RS485 GND
RS485 总线 GND
ESP32 节点 1 GND
ESP32 节点 2 GND
各节点 RS485 GND
各传感器 GND

只共 GND，不把多个开发板的 3V3 输出并联。

7.5 A/B 或战舰侧线路接反

调试过程中曾出现“有时有信号，有时全 no reply”的状态，后来确认战舰 V3 侧线曾接反，重新接回后通信恢复。RS485 模块之间的 A/B 命名在不同厂家资料中并不总是一致，接反时常见现象是总线有电平变化但 UART 解码全错。

修复方法是只对调一侧 A/B 做验证，并观察 @Q,DBG 中 S 是否从错误状态恢复为 0000。

7.6 LCD 白屏、花屏和显示区域异常

战舰 V3 LCD 调试阶段出现过 reset 后白屏、短暂黑屏、上半部分有字而下半部分花屏等现象。软件中加入了 LCD 控制器 ID 探测和不同初始化序列，并使用 FSMC 方式刷新显示。

最终 LCD 能显示节点在线状态、传感器值、超时次数和接收诊断。屏幕颜色的含义也在调试中明确：传感器字段里的 ESP_OK 只表示 ESP32 端某个传感器读取成功；整行红色或 LOST/NO REPLY 表示主站没有拿到该节点的有效 RS485 应答。这两个状态不能混淆。

7.7 轮询接收导致 USART ORE

在尝试提高刷新频率时，STM32 主站原先通过主循环轮询 USART3_SR 和 USART3_DR。当波特率提高到 38400 或 115200，并把 ESP32 应答延迟降到 10ms 左右时，STM32 端常见诊断为：

@Q,DBG=01,TO,L=1,N=1,S=0008
@Q,DBG=02,TO,L=1,N=1,S=0008

S=0008 对应 USART overrun error。说明字节已经进入 USART，但主循环没有及时读取，后续字节被覆盖。

修复方法是改为 USART3 接收中断和环形缓冲。修改后，主循环不直接等待硬件 RXNE，而是解析缓冲区中的完整行。该修复消除了主循环被 LCD、延时和字符串处理阻塞时丢字节的问题。

7.8 10ms 应答导致节点 02 残帧

在实现中断接收后，曾把 ESP32 响应延迟降到 10 ms。现场现象是：

T01、T02 持续增长，但屏幕显示 No reply

进一步开启 @Q,DBG 后发现：

@Q,DBG=01,OK,L=61,N=61,S=0000
@Q,DBG=02,TO,L=1,N=1,S=000A

S=000A 表示 FE + ORE，不是完全没有信号，而是主站只收到 1 个坏字节或残字节。与此同时，另一块 ESP32 能嗅探到节点 02 的完整 @D,ID=02... 回复，说明节点 02 确实发送了数据，但 STM32 端没有可靠解码。

修复方法是把两块 ESP32 都刷回 RS485_RESPONSE_DELAY_MS=120。其中 ID01 通过 USB-JTAG 端口刷写成功；ID02 的 USB-JTAG 端口在 RTS 自动复位时报 BrokenPipeError，改用 /dev/ttyACM0 这条 WCH 串口并降低烧录波特率到 115200 后刷写成功。

刷写后重新监听，两个节点均恢复：

@Q,DBG=01,OK,L=61,N=61,E=386,Z=1688,S=0000
@Q,DBG=02,OK,L=60,N=60,E=372,Z=1667,S=0000
@A,SUM,01=OK,...;02=OK,...

因此当前结论是：在现有桌面布线和外置 RS485 模块条件下，38400 + 120ms 是稳定档；10ms 应答需要进一步优化方向切换、总线终端/偏置、收发器模块质量或降低调试输出负载后再尝试。

9. 验证方法

9.1 构建验证

STM32：

make -C stm32-warship-v3-rs485-test

ESP32：

cd esp32-wroom-c6-workspace
./tools/idf.sh build

两者当前均可构建通过。

9.2 烧录注意事项

本次现场发现两块 ESP32 的可用烧录端口并不完全相同：

节点成功烧录方式
ID01 / MAC 末字节 0x24USB-JTAG 端口 /dev/ttyACM3
ID02 / MAC 末字节 0xECWCH 串口 /dev/ttyACM0，烧录波特率 115200

ID02 使用 USB-JTAG 端口时曾出现：

BrokenPipeError: [Errno 32] Broken pipe

这不是固件逻辑错误，而是该 USB 串口在自动复位/RTS 操作时不稳定。改用 WCH 串口后可以正常刷写。

9.3 运行验证

稳定运行时，应在任意 ESP32 monitor 或战舰串口输出中看到：

@Q,DBG=01,OK,L=61,N=61,...,S=0000
@Q,DBG=02,OK,L=60,N=60,...,S=0000
@A,SUM,01=OK,...;02=OK,...

若 LCD 显示 No reply，优先看接收诊断：

诊断判断
N=0STM32 没收到任何字节，优先查方向控制、A/B、GND、节点是否响应
N>0 且 S=0008USART 溢出，说明收到但主站没及时读
S=000A帧错误 + 溢出，通常是波特率、A/B、方向切换或响应太早导致坏帧
L≈60 且 S=0000完整收到节点应答

10. 后续改进建议

当前软件已经能稳定完成两节点采集和 LCD 显示。若后续继续追求 10Hz 级别刷新，可以按以下顺序推进：

  1. 先保持 38400 + 120ms，关闭逐次 @Q,DBG，只保留 5s @A,SUM，观察 5 分钟是否稳定。
  2. 将 RS485_RESPONSE_DELAY_MS 从 120ms 分级降低到 80ms、50ms、30ms，每一级至少观察 1 分钟。
  3. 若低于 30ms 出现 S=000A，先不要继续降延迟，应检查终端电阻、偏置、A/B 线长度、面包板接触和收发器模块质量。
  4. 若要长期追求更高刷新率，可以把调试 ASCII 帧改短，或切换到带 CRC 的二进制协议/Modbus RTU。
  5. 现场交付版建议关闭逐次 @Q,DBG，否则调试输出本身会增加总线负载。

11. 结论

本次软件调试的核心问题不是单个传感器读取，而是多节点 RS485 总线在战舰 V3 主站侧的接收可靠性。通过逐步排查可以得到以下结论：

  1. ESP32-C6 节点采集逻辑可用，BH1750、AM2302、PIR 均能形成 @D 数据帧。
  2. 战舰 V3 使用外置 RS485 模块和 USART3 PB10/PB11/PF12 是当前可复现方案。
  3. 主站轮询接收会在较高频通信下触发 USART ORE，必须改为中断接收和环形缓冲。
  4. 10ms 响应延迟在当前硬件条件下不稳定，节点 02 会出现残帧和 S=000A。
  5. 两块 ESP32 全部刷成 38400 + 120ms 后，最终得到 ID01 OK、ID02 OK、S=0000 的稳定状态。

因此，当前项目的软件交付状态建议固定为：38400 bps、ESP32 应答延迟 120ms、STM32 USART3 中断接收、LCD 5s 聚合显示、保留诊断帧用于继续现场观察。
