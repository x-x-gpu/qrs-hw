# ESP32-C6 与战舰 V3 烧录移植说明报告

日期：2026-06-16

## 1. 报告范围

本报告整理当前项目的烧录方式、烧录过程、可交付文件，以及别人把本文件夹拿到其它系统继续开发时需要注意的工程文件问题。本文不重新展开硬件接线细节，只围绕“怎么编译、怎么烧录、换电脑还能不能直接用”说明。

当前项目分为两套固件：

| 固件对象 | 工程目录 | 当前工程类型 | 是否有 Keil 工程 | 是否有 CubeMX `.ioc` |
|---|---|---|---|---|
| ESP32-C6 采集节点 | `esp32-wroom-c6-workspace/` | ESP-IDF / CMake | 不适用 | 不适用 |
| 战舰 V3 / STM32F103ZET6 主站 | `stm32-warship-v3-rs485-test/` | 裸机 Makefile 工程 | 没有 | 没有 |

结论先写在前面：当前仓库**有可以给战舰 V3 烧录的源码、Makefile、链接脚本和 `.elf/.bin` 产物**，但**没有 Keil `.uvprojx`，也没有 STM32CubeMX `.ioc`**。别人拿到文件夹后，可以在 Linux 下按 Makefile/OpenOCD 方式编译烧录；如果要用 Keil 或 CubeMX，需要重新建工程并手工导入源码与引脚/时钟配置。

0x0 bootloader/bootloader.bin
0x10000 esp32c6_wroom1_pipeline.bin
0x8000 partition_table/partition-table.bin

## 3. ESP32-C6 烧录方式

### 3.1 推荐方式：使用项目包装脚本

本项目推荐在 Linux 下使用：

```bash
cd esp32-wroom-c6-workspace
./tools/idf.sh build
./tools/idf.sh -p /dev/ttyACM0 flash
./tools/idf.sh -p /dev/ttyACM0 monitor
```

如果要烧录后直接打开 monitor：

```bash
./tools/idf.sh -p /dev/ttyACM0 flash monitor
```

其中 `/dev/ttyACM0` 需要替换成实际串口。ESP32-C6 开发板可能出现两类端口：

| 端口类型 | 常见设备名 | 说明 |
|---|---|---|
| USB Serial/JTAG | `/dev/ttyACM0`、`/dev/ttyACM1` | ESP32-C6 原生 USB 下载/日志 |
| USB-UART 桥 | `/dev/ttyUSB0` 或 WCH/CH34x 对应端口 | 部分开发板或外接串口 |

本项目曾遇到两块 ESP32 的可用烧录端口不同：一块可用 USB-JTAG 端口，另一块 USB-JTAG 自动复位不稳定，改用 WCH 串口并降低烧录波特率后成功。因此移植时不能固定认为所有板都是同一个 `/dev/ttyACM0`。

### 3.2 一体化传感器烧录脚本

项目还提供：

```bash
cd esp32-wroom-c6-workspace
./tools/flash-monitor-sensors.sh -p /dev/ttyACM0
```

该脚本会先构建，再烧录，最后进入 monitor。若不想进入 monitor：

```bash
./tools/flash-monitor-sensors.sh -p /dev/ttyACM0 --no-monitor
```

脚本内部会打印当前期望接线：

```text
BH1750/GY-302: SDA=GPIO6, SCL=GPIO7, VCC=3V3, GND=GND
AM2302/DHT22:  DATA=GPIO11, VCC=3V3, GND=GND
HC-SR501:      OUT=GPIO10, VCC=5V/VBUS, GND=GND
RS485 module:  TX=GPIO20, RX=GPIO21, DE,/RE=GPIO18, VCC=3V3, GND=GND
```

### 3.3 直接用 esptool 烧录已有 `.bin`

如果不重新编译，只使用当前 `build/` 下的产物，可以按 ESP-IDF 输出的命令烧录：

```bash
cd esp32-wroom-c6-workspace
python -m esptool --chip esp32c6 -b 460800 \
  --before default_reset --after hard_reset write_flash \
  --flash_mode dio --flash_size 2MB --flash_freq 80m \
  0x0 build/bootloader/bootloader.bin \
  0x8000 build/partition_table/partition-table.bin \
  0x10000 build/esp32c6_wroom1_pipeline.bin
```

也可以在 `build/` 目录下使用：

```bash
cd esp32-wroom-c6-workspace/build
python -m esptool --chip esp32c6 -b 460800 \
  --before default_reset --after hard_reset write_flash "@flash_args"
```

这种方式适合“只烧现成固件”。如果要改代码，应重新安装 ESP-IDF 并重新构建。

### 3.4 ESP-IDF 环境依赖

当前工程按 ESP-IDF v5.5.1 配置，`tools/idf.sh` 默认寻找：

```text
$HOME/.espressif/tools/activate_idf_v5.5.1.sh
```

脚本中 `IDF_ACTIVATE` 可以覆盖：

```bash
IDF_ACTIVATE=/path/to/activate_idf_v5.5.1.sh ./tools/idf.sh build
```

换电脑时需要注意：

| 项目 | 当前情况 | 移植注意 |
|---|---|---|
| ESP-IDF 版本 | v5.5.1 | 建议使用相同大版本，避免驱动 API 差异 |
| 目标芯片 | `esp32c6` | 首次构建可执行 `./tools/idf.sh set-target esp32c6` |
| Python 虚拟环境 | 本机位于 `$HOME/.espressif/...` | 不应复制本机 venv，换电脑重新安装 |
| CMake/Ninja | ESP-IDF 管理工具链 | `tools/idf.sh` 会优先使用 ESP-IDF 管理版本 |
| 串口权限 | 依赖 Linux 用户组/udev | 可能需要加入 `dialout` 或配置 udev |

## 4. 战舰 V3 / STM32 烧录方式

### 4.1 推荐方式：Makefile + OpenOCD + ST-Link

当前 STM32 工程不是 Keil 工程，而是 GNU Arm 工具链工程。构建命令：

```bash
make -C stm32-warship-v3-rs485-test
```

当前验证输出：

```text
text   data    bss    dec    hex
7576      0    664   8240   2030
```

烧录命令：

```bash
make -C stm32-warship-v3-rs485-test flash
```

`Makefile` 中的烧录规则为：

```make
openocd -f interface/stlink.cfg -f target/stm32f1x.cfg \
  -c "program build/warship_v3_rs485_test.elf verify reset exit"
```

这意味着默认烧录器是 ST-Link，目标芯片族是 STM32F1。若别人使用 J-Link、DAPLink 或其它烧录器，需要改 OpenOCD interface 配置。

### 4.2 直接烧录已有 `.elf`

如果只烧现有固件，可在工程目录执行：

```bash
cd stm32-warship-v3-rs485-test
openocd -f interface/stlink.cfg -f target/stm32f1x.cfg \
  -c "program build/warship_v3_rs485_test.elf verify reset exit"
```

这种方式会使用 ELF 内部地址信息，适合 OpenOCD。

### 4.3 直接烧录已有 `.bin`

如果使用 STM32CubeProgrammer、Keil 的 Flash 工具或其它通用烧录软件，可以使用：

```text
stm32-warship-v3-rs485-test/build/warship_v3_rs485_test.bin
```

写入地址应为 STM32F103ZET6 内部 Flash 起始地址：

```text
0x08000000
```

注意：`.bin` 没有地址元数据，烧录软件必须手工指定地址；`.elf` 则包含地址信息。

### 4.4 STM32 工具链依赖

别人换电脑后，如果要从源码重新构建，需要安装：

| 工具 | 作用 |
|---|---|
| `arm-none-eabi-gcc` | 编译 ARM Cortex-M3 C 代码 |
| `arm-none-eabi-objcopy` | 从 ELF 生成 BIN |
| `arm-none-eabi-size` | 输出固件段大小 |
| `make` | 执行 Makefile |
| `openocd` | 通过 ST-Link 烧录 |

Ubuntu 下通常可安装：

```bash
sudo apt-get install make gcc-arm-none-eabi binutils-arm-none-eabi openocd
```

不同 Linux 发行版包名可能不同；Windows 下可以安装 Arm GNU Toolchain、Make 和 OpenOCD，或改用 Keil 重新建工程。

## 5. 不存在的 Keil / CubeMX 文件

当前文件夹中没有以下文件：

```text
*.uvprojx
*.uvoptx
*.uvproj
*.uvopt
*.ioc
*.project
*.cproject
*.mxproject
```

因此别人拿到本文件夹后：

1. 不能双击 Keil 工程直接打开。
2. 不能用 CubeMX 打开 `.ioc` 重新生成初始化代码。
3. 可以使用 Linux Makefile 编译和烧录 STM32。
4. 可以使用 ESP-IDF 编译和烧录 ESP32-C6。
5. 若必须用 Keil/CubeMX，需要重新建工程。

### 5.1 如果要移植成 Keil 工程

需要新建 Keil 工程并手动配置：

| 项目 | 当前来源 | Keil 中需要做什么 |
|---|---|---|
| 目标芯片 | `STM32F103ZET6` | 新建目标选择该芯片或同系列容量匹配型号 |
| 源码 | `main.c`、`startup.c` | 加入工程源文件 |
| Flash/RAM 布局 | `stm32f103ze.ld` | 在 Keil target 中配置 IROM/IRAM，或使用 Keil scatter 文件 |
| 启动文件 | 当前 `startup.c` | 可继续用 C 启动文件，也可换成 Keil 标准 startup 汇编 |
| 外设初始化 | `main.c` 裸寄存器代码 | 不依赖 HAL，不需要 CubeMX 生成 |
| 中断向量 | `startup.c` 中向量表 | 确保 `USART3_IRQHandler` 位于正确 IRQ |
| 编译宏/优化 | `Makefile` | 按 Cortex-M3、Thumb、优化等级配置 |

当前代码直接操作寄存器，不依赖 STM32 HAL/标准库。因此迁移到 Keil 时，最重要的是保证启动文件、向量表、链接地址和系统时钟假设一致。

### 5.2 如果要移植成 CubeMX / CubeIDE 工程

CubeMX 不能从当前 `main.c` 自动反推出 `.ioc`。若要重建 `.ioc`，至少要重新配置：

| 功能 | 当前实际使用 | CubeMX 中要配置 |
|---|---|---|
| MCU | STM32F103ZET6 | 选择对应芯片 |
| USART3 TX | PB10 | USART3 Asynchronous TX |
| USART3 RX | PB11 | USART3 Asynchronous RX |
| RS485 方向控制 | PF12 | GPIO Output |
| LCD/FSMC | 当前由 `main.c` 裸寄存器控制 | 需要按战舰 V3 LCD 连接重新配置 FSMC/GPIO |
| SysTick/延时 | 裸机实现 | 可用 HAL tick 或保留裸机逻辑 |
| USART3 中断 | `USART3_IRQHandler` | 使能 USART3 global interrupt |

迁移到 CubeIDE 后有两种策略：

1. 保留现有裸寄存器 `main.c`，只让 CubeMX 负责工程壳和启动文件。
2. 全部改成 HAL/LL 写法，但这相当于重写 STM32 主站部分，风险较高。

本项目当前交付更适合第一种：把现有代码作为已经验证的主逻辑，尽量少改。

## 6. 换系统开发的可预见问题

### 6.1 Linux 到 Linux

同为 Linux 时迁移成本最低。需要处理的问题主要是：

| 问题 | 表现 | 处理 |
|---|---|---|
| ESP-IDF 安装路径不同 | `tools/idf.sh` 找不到 activate 脚本 | 设置 `IDF_ACTIVATE` 或重新安装 ESP-IDF v5.5.1 |
| 串口名不同 | `/dev/ttyACM0` 不存在 | 用 `ls /dev/ttyACM* /dev/ttyUSB*` 或 `ls /dev/serial/by-id` 查找 |
| 串口权限不足 | flash/monitor permission denied | 加入 `dialout` 组或配置 udev |
| ST-Link 权限不足 | OpenOCD 找不到设备或 permission denied | 配置 udev 或用 sudo 验证 |
| `build/` 内绝对路径失效 | CMake/Ninja 构建异常 | 删除 `build/` 后重新 `./tools/idf.sh build` |

### 6.2 Linux 到 Windows

Windows 下不能直接运行 `.sh` 脚本，除非使用 WSL/Git Bash/MSYS2。可选方案：

| 方案 | ESP32 | STM32 |
|---|---|---|
| WSL2 | 可运行 `tools/idf.sh`，但 USB 透传要额外配置 | OpenOCD/ST-Link 也需 USB 透传 |
| 原生 Windows | 使用 ESP-IDF PowerShell/CMD 环境，参考 `tools/*.ps1` | 安装 Arm GNU Toolchain + Make + OpenOCD，或改 Keil |
| Keil 路线 | 不适用 | 需要重新建 Keil 工程 |

如果只是烧现成固件，Windows 下可用 Espressif Flash Download Tool / esptool 烧 ESP32，用 STM32CubeProgrammer 烧 STM32 `.bin`。如果要继续开发，建议按各平台官方方式安装完整工具链。

### 6.3 Linux 到 macOS

macOS 下 ESP-IDF 支持较好，但 STM32 OpenOCD 和 Arm 工具链需要额外安装。串口设备名通常是：

```text
/dev/cu.usbmodem*
/dev/cu.usbserial*
```

脚本中的 `/dev/ttyACM0` 需要替换。OpenOCD interface 文件路径通常仍可使用，但具体安装路径和权限模型与 Linux 不同。

## 10. 结论

当前文件夹可以作为 Linux 开发交付包使用：ESP32-C6 使用 ESP-IDF，战舰 V3 使用 Makefile/OpenOCD。别人拿到后，只要安装相应工具链，就可以重新编译、烧录和继续开发。

但它不是 Keil/CubeMX 交付包。若课程或老师要求“Keil 工程文件”或“CubeMX 工程文件”，当前目录还缺少 `.uvprojx` 和 `.ioc`，需要额外重建。重建时应以 `stm32-warship-v3-rs485-test/main.c`、`startup.c`、`stm32f103ze.ld` 和 `Makefile` 为准，避免把已经验证过的 USART3/RS485/LCD 逻辑改坏。
