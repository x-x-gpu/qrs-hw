ESP32-C6 与战舰 V3 烧录移植说明报告

日期：2026-06-16

1. 报告范围

本报告整理当前项目的烧录方式、烧录过程、可交付文件，以及别人把本文件夹拿到其它系统继续开发时需要注意的工程文件问题。本文不重新展开硬件接线细节，只围绕“怎么编译、怎么烧录、换电脑还能不能直接用”说明。

当前项目分为两套固件：

固件对象工程目录当前工程类型是否有 Keil 工程是否有 CubeMX .ioc
ESP32-C6 采集节点esp32-wroom-c6-workspace/ESP-IDF / CMake不适用不适用
战舰 V3 / STM32F103ZET6 主站stm32-warship-v3-rs485-test/裸机 Makefile 工程没有没有

结论先写在前面：当前仓库有可以给战舰 V3 烧录的源码、Makefile、链接脚本和 .elf/.bin 产物，但没有 Keil .uvprojx，也没有 STM32CubeMX .ioc。别人拿到文件夹后，可以在 Linux 下按 Makefile/OpenOCD 方式编译烧录；如果要用 Keil 或 CubeMX，需要重新建工程并手工导入源码与引脚/时钟配置。

3. ESP32-C6 烧录方式

3.1 推荐方式：使用项目包装脚本

cd esp32-wroom-c6-workspace
./tools/idf.sh build
./tools/idf.sh -p /dev/ttyACM0 flash
./tools/idf.sh -p /dev/ttyACM0 monitor

如果要烧录后直接打开 monitor：

./tools/idf.sh -p /dev/ttyACM0 flash monitor
端口类型常见设备名说明
USB Serial/JTAG/dev/ttyACM0、/dev/ttyACM1ESP32-C6 原生 USB 下载/日志
USB-UART 桥/dev/ttyUSB0 或 WCH/CH34x 对应端口部分开发板或外接串口

本项目曾遇到两块 ESP32 的可用烧录端口不同：一块可用 USB-JTAG 端口，另一块 USB-JTAG 自动复位不稳定，改用 WCH 串口并降低烧录波特率后成功。因此移植时不能固定认为所有板都是同一个 /dev/ttyACM0。

3.2 一体化传感器烧录脚本

cd esp32-wroom-c6-workspace
./tools/flash-monitor-sensors.sh -p /dev/ttyACM0

若不想进入 monitor：

./tools/flash-monitor-sensors.sh -p /dev/ttyACM0 --no-monitor

脚本内部会打印当前期望接线：

BH1750/GY-302: SDA=GPIO6, SCL=GPIO7, VCC=3V3, GND=GND
AM2302/DHT22:  DATA=GPIO11, VCC=3V3, GND=GND
HC-SR501:      OUT=GPIO10, VCC=5V/VBUS, GND=GND
RS485 module:  TX=GPIO20, RX=GPIO21, DE,/RE=GPIO18, VCC=3V3, GND=GND

3.3 直接用 esptool 烧录已有 .bin

cd esp32-wroom-c6-workspace
python -m esptool --chip esp32c6 -b 460800 \
  --before default_reset --after hard_reset write_flash \
  --flash_mode dio --flash_size 2MB --flash_freq 80m \
  0x0 build/bootloader/bootloader.bin \
  0x8000 build/partition_table/partition-table.bin \
  0x10000 build/esp32c6_wroom1_pipeline.bin

也可以在 build/ 目录下使用：

cd esp32-wroom-c6-workspace/build
python -m esptool --chip esp32c6 -b 460800 \
  --before default_reset --after hard_reset write_flash "@flash_args"

这种方式适合“只烧现成固件”。如果要改代码，应重新安装 ESP-IDF 并重新构建。

3.4 ESP-IDF 环境依赖

当前工程按 ESP-IDF v5.5.1 配置，tools/idf.sh 默认寻找：

$HOME/.espressif/tools/activate_idf_v5.5.1.sh

脚本中 IDF_ACTIVATE 可以覆盖：

IDF_ACTIVATE=/path/to/activate_idf_v5.5.1.sh ./tools/idf.sh build
项目当前情况移植注意
ESP-IDF 版本v5.5.1建议使用相同大版本，避免驱动 API 差异
目标芯片esp32c6首次构建可执行 ./tools/idf.sh set-target esp32c6
Python 虚拟环境本机位于 $HOME/.espressif/...不应复制本机 venv，换电脑重新安装
CMake/NinjaESP-IDF 管理工具链tools/idf.sh 会优先使用 ESP-IDF 管理版本
串口权限依赖 Linux 用户组/udev可能需要加入 dialout 或配置 udev

4. 战舰 V3 / STM32 烧录方式

4.1 推荐方式：Makefile + OpenOCD + ST-Link

当前 STM32 工程不是 Keil 工程，而是 GNU Arm 工具链工程。构建命令：

make -C stm32-warship-v3-rs485-test

当前验证输出：

text   data    bss    dec    hex
7576      0    664   8240   2030

烧录命令：

make -C stm32-warship-v3-rs485-test flash

Makefile 中的烧录规则为：

openocd -f interface/stlink.cfg -f target/stm32f1x.cfg \
  -c "program build/warship_v3_rs485_test.elf verify reset exit"

这意味着默认烧录器是 ST-Link，目标芯片族是 STM32F1。若别人使用 J-Link、DAPLink 或其它烧录器，需要改 OpenOCD interface 配置。

4.2 直接烧录已有 .elf

cd stm32-warship-v3-rs485-test
openocd -f interface/stlink.cfg -f target/stm32f1x.cfg \
  -c "program build/warship_v3_rs485_test.elf verify reset exit"

这种方式会使用 ELF 内部地址信息，适合 OpenOCD。

4.3 直接烧录已有 .bin

如果使用 STM32CubeProgrammer、Keil 的 Flash 工具或其它通用烧录软件，可以使用：

stm32-warship-v3-rs485-test/build/warship_v3_rs485_test.bin

写入地址应为 STM32F103ZET6 内部 Flash 起始地址：

0x08000000

注意：.bin 没有地址元数据，烧录软件必须手工指定地址；.elf 则包含地址信息。

当前文件夹中没有以下文件：

5.1 如果要移植成 Keil 工程

项目当前来源Keil 中需要做什么
目标芯片STM32F103ZET6新建目标选择该芯片或同系列容量匹配型号
源码main.c、startup.c加入工程源文件
Flash/RAM 布局stm32f103ze.ld在 Keil target 中配置 IROM/IRAM，或使用 Keil scatter 文件
启动文件当前 startup.c可继续用 C 启动文件，也可换成 Keil 标准 startup 汇编
外设初始化main.c 裸寄存器代码不依赖 HAL，不需要 CubeMX 生成
中断向量startup.c 中向量表确保 USART3_IRQHandler 位于正确 IRQ
编译宏/优化Makefile按 Cortex-M3、Thumb、优化等级配置

当前代码直接操作寄存器，不依赖 STM32 HAL/标准库。因此迁移到 Keil 时，最重要的是保证启动文件、向量表、链接地址和系统时钟假设一致。

5.2 如果要移植成 CubeMX / CubeIDE 工程

功能当前实际使用CubeMX 中要配置
MCUSTM32F103ZET6选择对应芯片
USART3 TXPB10USART3 Asynchronous TX
USART3 RXPB11USART3 Asynchronous RX
RS485 方向控制PF12GPIO Output
LCD/FSMC当前由 main.c 裸寄存器控制需要按战舰 V3 LCD 连接重新配置 FSMC/GPIO
SysTick/延时裸机实现可用 HAL tick 或保留裸机逻辑
USART3 中断USART3_IRQHandler使能 USART3 global interrupt

迁移到 CubeIDE 后有两种策略：保留现有裸寄存器 main.c，只让 CubeMX 负责工程壳和启动文件；或全部改成 HAL/LL 写法。后者相当于重写 STM32 主站部分，风险较高。

6. 换系统开发的可预见问题

6.1 Linux 到 Linux

问题表现处理
ESP-IDF 安装路径不同tools/idf.sh 找不到 activate 脚本设置 IDF_ACTIVATE 或重新安装 ESP-IDF v5.5.1
串口名不同/dev/ttyACM0 不存在用 ls /dev/ttyACM* /dev/ttyUSB* 或 ls /dev/serial/by-id 查找
串口权限不足flash/monitor permission denied加入 dialout 组或配置 udev
ST-Link 权限不足OpenOCD 找不到设备或 permission denied配置 udev 或用 sudo 验证
build/ 内绝对路径失效CMake/Ninja 构建异常删除 build/ 后重新 ./tools/idf.sh build

6.2 Linux 到 Windows

方案ESP32STM32
WSL2可运行 tools/idf.sh，但 USB 透传要额外配置OpenOCD/ST-Link 也需 USB 透传
原生 Windows使用 ESP-IDF PowerShell/CMD 环境，参考 tools/*.ps1安装 Arm GNU Toolchain + Make + OpenOCD，或改 Keil
Keil 路线不适用需要重新建 Keil 工程

如果只是烧现成固件，Windows 下可用 Espressif Flash Download Tool / esptool 烧 ESP32，用 STM32CubeProgrammer 烧 STM32 .bin。如果要继续开发，建议按各平台官方方式安装完整工具链。

6.3 Linux 到 macOS

macOS 下 ESP-IDF 支持较好，但 STM32 OpenOCD 和 Arm 工具链需要额外安装。串口设备名通常是：

/dev/cu.usbmodem*
/dev/cu.usbserial*

脚本中的 /dev/ttyACM0 需要替换。OpenOCD interface 文件路径通常仍可使用，但具体安装路径和权限模型与 Linux 不同。

10. 结论

当前文件夹可以作为 Linux 开发交付包使用：ESP32-C6 使用 ESP-IDF，战舰 V3 使用 Makefile/OpenOCD。别人拿到后，只要安装相应工具链，就可以重新编译、烧录和继续开发。

但它不是 Keil/CubeMX 交付包。若课程或老师要求“Keil 工程文件”或“CubeMX 工程文件”，当前目录还缺少 .uvprojx 和 .ioc，需要额外重建。重建时应以 stm32-warship-v3-rs485-test/main.c、startup.c、stm32f103ze.ld 和 Makefile 为准，避免把已经验证过的 USART3/RS485/LCD 逻辑改坏。
